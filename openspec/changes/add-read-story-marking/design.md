## Context

The app is an Angular 9 SPA with no per-reader state today. The only existing persistence is `SettingsService`, which reads and writes individual `localStorage` keys directly and exposes a plain `settings` object that components bind to. Feeds render `Story` objects from the Hacker News API through `ItemComponent`; a story's title is either an external anchor (`href`) or an internal `routerLink` to the item-details page. Themes are generated by the `theme()` SCSS mixin in `_themes.scss`, which takes every colour as a positional argument, so any new themed colour has to be threaded through all three theme invocations.

See proposal.md for motivation and specs/read-story-marking/spec.md for the required behavior.

## Goals / Non-Goals

**Goals:**
- One owner of read state that both the feed items and the item-details page use.
- Read state readable synchronously during template rendering, so a feed row can render its treatment without an extra change-detection pass.
- The read treatment participates in the theme engine rather than hard-coding a colour.

**Non-Goals:**
- Syncing read state between devices or to any backend.
- A UI to clear or review read stories, or an "unread" toggle.
- Marking comments, users, or polls as read.

## Decisions

**A dedicated `ReadStoriesService` rather than extending `SettingsService`.** Read state is per-story data with its own size bound and eviction, not a user preference; `SettingsService` is a flat bag of scalar settings bound directly into templates. Keeping them apart avoids widening `Settings` with a collection that no settings UI controls. Alternative considered: another `localStorage` key inside `SettingsService` — rejected because eviction logic and set semantics do not fit that shape.

**An in-memory `Set<number>` backed by a single `localStorage` key.** The service loads the persisted ids once at construction into a `Set` and writes the whole set back on each new mark. Feed rendering asks the service per row, so lookup must be O(1) and synchronous; reading and parsing `localStorage` per row would not be. Writes are rare (once per story opened), so rewriting the whole key is cheap. Alternative considered: one `localStorage` key per story id — rejected because it makes the cap and eviction impossible to enforce without enumerating storage.

**Insertion-ordered array as the stored representation.** The set is persisted as a JSON array in the order ids were first recorded, which is what makes "discard the entries recorded longest ago" well-defined after a reload. Re-marking an already-read story is a no-op, so its original position — and therefore its eviction order — is preserved.

**Cap of 1000 ids, evicting from the front.** A few tens of kilobytes at most, far below any `localStorage` quota, while covering many pages of feed history. The cap is a service-level constant, not a setting.

**All storage access is wrapped in try/catch and treats failure as "nothing is read".** `localStorage` throws in private-mode and storage-disabled browsers, and the persisted value can be corrupt or hand-edited. The spec requires the app keep working in that case, so the service degrades to an empty in-memory set rather than propagating the error; a failed write leaves the in-memory set marked so the current session still shows the treatment.

**Marking happens on the reader's action, not on render.** `ItemComponent` marks on activation of the title link (both the external-anchor and internal-router branches), and `ItemDetailsComponent` marks when its route params resolve. The item-details hook is what covers a story opened directly by URL or by the comments link rather than the title. Alternative considered: marking centrally on router navigation to `/item/:id` — rejected because it would not cover external links, which are the common case in these feeds.

**The read treatment is a theme colour threaded through the `theme()` mixin.** `ItemComponent` puts a `read` class on the title, and each theme supplies a de-emphasised title colour derived from its existing subtext colour. Hard-coding a grey would be illegible against the amoled-black theme.

## Risks / Trade-offs

- **A `isRead(id)` call in the template runs on every change-detection cycle** → the call is a `Set.has` on an in-memory set, so it stays cheap even at 30 rows per feed.
- **External links are marked read on activation, not on successful navigation** → a reader who opens a link and immediately dismisses it still has it marked; accepted, since intent to read is the signal the feature is about and there is no reliable completion event for an external navigation.
- **Read state is per-device and silently lost when the browser clears site data** → accepted and documented in the spec; there is no account to attach it to.
- **The eviction cap can drop stories the reader really did read** → only past 1000 stories, and the consequence is a story rendering as unread.
